# Задача: быстрая адаптация к процедурно собираемым трассам Mars Rover

Ты получаешь эту задачу с чистого листа. Ниже — всё, что нужно знать про среду,
уже перепробованные подходы и их результаты, и что конкретно нужно сделать.
Не считай прошлые попытки авторитетным потолком возможностей — если видишь
более простое или более сильное решение, предлагай и пробуй его.

## 1. Среда

Репозиторий: `environment/` (движок на C++20 + pybind11) и `baselines/`
(Python-агенты поверх stable-baselines3). Установка:

```bash
pip install -e ./environment --no-build-isolation
pip install -e ./baselines --no-build-isolation
```

Марсоход едет по 1D-трассе (ось x), физика — гусеницы/колёса, гравитация,
баллистика, энергия. Наблюдение — вектор физических величин (позиция, скорость,
наклон, контакт с поверхностью, лидар-скан локального рельефа, энергия и т.д.),
никакой привилегированной информации о типе механики не передаётся.

Действия — 15 дискретных макросов (`mars_rover_env/actions.py:ACTION_MACROS`),
каждый — комбинация битовых флагов низкоуровневого контроллера (газ, тормоз,
руление по тангажу для баллистических прыжков, переключение передачи и т.д.).

### Трасса — это цепочка биомов, не один фиксированный биом

Ключевая идея эксперимента: при `chain_biomes=true` (это дефолт для
`env.yaml`/`play.yaml`) каждый `env.reset(seed=..., options={"trial_start": True})`
случайно **собирает новую трассу** длиной `chain_zone_count` зон (по умолчанию
10-14), каждая зона — 30-70м, засеменена своим биомом:

- Первая зона всегда одна из 8 "опорных" (anchor) биомов — простых, дающих
  разгон (`normal`, `sand`, `ice`, `mud`, `wind`, `low_gravity`, `crust`,
  `liquid`).
- Остальные зоны берутся из пула `train`-биомов (или `test` — held-out сплит
  для валидации).
- Пул `train`/`test`-биомов **не статичен**: часть биомов рукописная, часть —
  сгенерирована LLM-пайплайном (`mars_rover_env/tools/generate_biomes.py`) и
  перегенерируется в начале каждого прогона (`bootstrap_run.py --replace`),
  так что от запуска к запуску набор механик за опорной зоной меняется.

Отсюда и постановка: агент не может выучить фиксированную трассу наизусть —
ему нужно быстро (за несколько попыток/шагов) приспособиться к конкретной,
только что собранной последовательности незнакомых механик. Это и есть
"адаптация", которую мы измеряем — не classic meta-RL с фиксированным
распределением задач, а буквально каждый раз новая, никогда раньше не
виденная трасса.

`episodes_per_trial` — количество "жизней": N эпизодов подряд идут на ОДНОЙ
и той же зафиксированной цепочке (`trial_mechanic_seed_` не меняется), потом
при `trial_start=True` собирается новая цепочка. Это единственный канал, через
который агент может "адаптироваться внутри трайла" — за счёт градиентных
шагов между попытками (см. `evaluate_adaptation_speed.py`) или за счёт
рекуррентной памяти (RL2-подход — см. раздел 3, уже испробован и провалился).

### Ревард — плотный, не бинарный

`environment/cpp/src/reward.cpp`:

```cpp
reward = (x - previous_x) * progress_scale     // += на каждом шаге за метры вперёд
        - energy_cost * energy_cost_scale
        - flip_penalty   (если перевернулся)
        - stuck_penalty  (если признан застрявшим)
        - hard_contact_penalty * damage
        + finish_bonus   (разово, только при полном прохождении всей цепочки)
```

`progress_scale=1.0`, `energy_cost_scale=0.01`, `finish_bonus=100`,
`flip_penalty`/`stuck_penalty` различаются между `env.yaml` (300/300, для
тренировки — жёстко карает) и `play.yaml` (5/0.05, для игры руками). Сигнал
за прогресс есть КАЖДЫЙ шаг, это НЕ sparse-reward задача в классическом
смысле "награда только за финиш".

### Конфиги

- `environment/python/mars_rover_env/configs/env.yaml` — тренировочный конфиг,
  `finish_x=800`, `chain_biomes=true`, `chain_zone_count=14`.
- `environment/python/mars_rover_env/configs/play.yaml` — для игры руками,
  `chain_zone_count=10`.
- Оба можно переопределять флагами `MarsRoverEnv(...)` /
  `MarsRoverSb3VecEnv(...)`.

## 2. Инструменты пайплайна (уже готовы, можно использовать как есть)

- `scripts/run_full_pipeline.sh` — Linux, одна команда:
  переустановка/сборка → обновление LLM-биомов (train+test, с difficulty
  gate) → обучение нескольких кандидатов → оценка адаптации → агрегация.
- `scripts/windows/full_pipeline.ps1` — то же самое на Windows.
- `baselines/python/baselines/evaluate_adaptation_speed.py` —
  протокол валидации: генерирует пачку свежих трасс, для каждого чекпоинта
  меряет число попыток/шагов до достижения `--target-distance`, усредняет.
  Это и есть метрика "кто быстрее адаптируется".
- MLflow: `tracking_uri=http://swagstation.netcraze.pro:4249`,
  `experiment_name=mars-rover-meta-rl` (id 18). Обёртка —
  `baselines/tracking.py:MLflowRun`. **Залогируй туда свой прогон**:
  параметры метода, кривую обучения, финальные метрики адаптации, ссылку на
  чекпоинт.

## 3. Что уже испробовано и провалилось — не повторяй один-в-один

| Подход | Результат |
|---|---|
| RL2 (рекуррентная политика, учится адаптироваться через скрытое состояние) | Едва учится двигаться (auc ≈ -0.005) без дистилляции + KL-якоря от уже компетентной политики. Хуже остальных. |
| MAML | Отклонён без попытки — вторые производные через PPO inner loop дорого и нестабильно на этом стеке (SB3 + батч-энв). Если у тебя есть способ сделать это практично — попробуй, это не железный запрет. |
| Reptile (first-order meta-learning, короткие бёрсты PPO на каждой новой цепочке + `meta_theta += lr*(theta_after_burst - meta_theta)`) | 0% success на `target_distance=60м` даже на 100M env-шагов на кандидата. |
| Vanilla PPO (без meta-learning, просто длинное обучение на потоке случайных цепочек) | То же самое: 0% success, ~3.5-4.3м средняя лучшая дистанция на трассе. Неотличимо от Reptile. |
| Warm-start (трансплантация весов из робастного PPO-чекпоинта, обученного на одиночных биомах, в модель с новым action-space) | Не помогло вообще — тёплый и холодный старт дают статистически одинаковый результат. |
| Увеличение бюджета обучения 15M → 100M шагов (×7) | **Не сдвинуло результат ни на йоту.** Это самый важный отрицательный факт: узкое место не в количестве шагов. |

Дополнительное наблюдение из последнего прогона: для одного и того же сида
трайла все 4 кандидата (разные алгоритмы/warm-start) проезжают почти
одинаковое расстояние и делают почти одинаковое число шагов до конца попытки.
Это означает, что исход трайла определяется в первую очередь конкретной
цепочкой биомов данного сида, а не тем, чему научилась модель — то есть ни
один кандидат реально не научился объезжать конкретные механики, они
упираются в одну и ту же структурную стену независимо от политики. Это
похоже на симптом вырожденной политики (коллапс к почти нулевому газу /
избегание риска из-за штрафов) или на то, что базовое, "не мета" вождение по
длинной цепочке само по себе не осваивается за разумное время — то есть
проблема ниже уровня "какой мета-алгоритм лучше".

## 4. Что нужно сделать

1. **Придумай и обоснуй метод** — не обязательно из списка выше. Можно:
   - другая схема reward-шейпинга (например, награда за прогресс внутри
     каждой отдельной зоны, а не только по общему x);
   - curriculum по длине цепочки (начать с 1-2 зон, постепенно растить до
     полной длины);
   - диагностика вырожденности политики перед тем, как усложнять алгоритм
     (энтропия действий, распределение выбранных макросов на трассе);
   - другая архитектура/представление наблюдений;
   - что-то своё.
2. **Реализуй его** в `baselines/` (новый скрипт по образцу
   `train_reptile_ppo.py`/`train_robust_ppo.py`) или патчами к существующим.
3. **Обучи и оцени** через `evaluate_adaptation_speed.py` (или свой
   аналогичный протокол, если метрика "успех за N попыток" тебе не подходит —
   но тогда явно обоснуй замену).
4. **Залогируй в MLflow** (эксперимент `mars-rover-meta-rl`) — параметры,
   кривую обучения, финальные метрики, честный вывод: помогло или нет и
   почему, по твоей гипотезе.
5. Не нужно скрывать отрицательный результат, если он получился —
   предыдущие попытки тоже были отрицательными, и это ценная информация.
